# Learning Architects / Signal

> A five-agent, evidence-led learning-response organisation that turns a **live Google Workspace product update** into a traceable training opportunity, solution specification, working prototype scope, adoption communications, and executive rollout plan.

This project was designed for the NCI H9CEAI *Build an Agentic Organisation* assessment. It demonstrates exactly five specialised AI agents—**Researcher → Designer → Maker → Communicator → Manager**—whose structured outputs are passed cumulatively through a single auditable pipeline.

## Why this is agentic

| Agent | Responsibility | Handoff artefact |
|---|---|---|
| Researcher | Fetches and interprets current Google Workspace release evidence. | Evidence-backed opportunity brief. |
| Designer | Converts the opportunity into a human-centred learning response. | Learning journey and acceptance criteria. |
| Maker | Translates the design into an implementable prototype scope and test plan. | Build/quality artefact. |
| Communicator | Produces accurate stakeholder adoption communications. | Targeted change-activation plan. |
| Manager | Reconciles the complete chain into a governed operational recommendation. | Executive plan, risks, KPIs, and next actions. |

Every persisted stage record contains `run_id`, `agent_name`, `input_artifact_ids`, `source_evidence`, `assumptions`, `decision_rationale`, `output`, `quality_checks`, and `created_at`. The dashboard exposes these values under a visible, copyable audit run ID.

## The mandatory live-data query

`server/agents/liveWorkspaceFeed.ts` contains the clearly labelled function:

```ts
fetchLiveGoogleWorkspaceUpdates()
```

It requests the official public [Google Workspace developer release-notes feed](https://developers.google.com/feeds/workspace-release-notes.xml) **at the moment a new run begins**. The function appends a timestamped query parameter, uses `cache: "no-store"`, validates the HTTP response, and stores the actual retrieval timestamp, request URL, status, and returned feed entries as Researcher source evidence. It does not read hardcoded, copied, persisted, or cached update values.

## Secure runtime design

All LLM calls occur in `server/agents/pipelineService.ts` through the server-side built-in LLM integration. The browser never receives the model, database, or authentication credentials. The source code contains no committed secret. See [`docs/environment-configuration.md`](docs/environment-configuration.md) for the managed configuration design and [`docs/architecture.md`](docs/architecture.md) for the full traceability diagram.

## Local development

This repository is a full-stack TypeScript project built with React, Vite, Express, tRPC, Drizzle, and MySQL/TiDB.

```bash
pnpm install
pnpm drizzle-kit generate
pnpm dev
```

The project needs a server environment that supplies the following values securely: `DATABASE_URL`, `JWT_SECRET`, `BUILT_IN_FORGE_API_URL`, and `BUILT_IN_FORGE_API_KEY`. Never place their values in the repository, browser bundle, GitHub Actions variables exposed to the client, or submission zip.

Apply the database migration generated by `pnpm drizzle-kit generate` before running a fresh deployment. The schema defines `pipelineRuns` and `pipelineArtifacts`, which preserve the complete audit chain.

## Tests and quality checks

```bash
pnpm check
pnpm test
pnpm build:pages
```

The test suite verifies that the solution contains the five required specialised agents and that live research retrieval issues a fresh no-store request rather than substituting a static value. A successful end-to-end test run should persist five artefacts for one completed run ID.

## Public GitHub Pages dashboard

The public marker interface uses GitHub Pages and is built via:

```bash
pnpm build:pages
```

The included GitHub Action deploys the static front end to:

```text
https://naosantana228-web.github.io/BuildanAgenticOrganisation/
```

Before public deployment, set the protected API origin in `client/public/config.js`. This file contains only a URL and no credential. Detailed deployment steps are in [`docs/github-pages-deployment.md`](docs/github-pages-deployment.md).

> **Important:** GitHub Pages hosts the public interface only. The server must be hosted separately with the required secret environment variables and database. The dashboard then calls that protected HTTPS API; CORS is restricted to GitHub Pages, local development, or same-origin requests.

## Important limitations and safeguards

This is an educational prototype, not an automated policy-authoring or employment-decision system. It uses public product-release evidence and does not ingest real employee training-request data in the sample run. Before any organisational rollout, a responsible product owner, learning lead, privacy function, accessibility lead, and relevant security stakeholders should review the source interpretation and final Manager recommendation.
